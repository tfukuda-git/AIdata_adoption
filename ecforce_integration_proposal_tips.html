ecforce × Mico Engage AI 連携 提案Tips

Mico社内・技術営業用プレイブック / ecforceをお使いの企業に連携を提案するときの勘所

大原則：MEは受け身（取込/送出を分ける） 選定軸：リアルタイム要否でA/B 中間サーバ：顧客準備（Micoは用意しない） 更新：2026/06

0. 大前提 — ME は「受け身」。まず“向き”を分ける

MEは自分からデータを取りに行かない。MEのAPIを「誰かが呼ぶ」ことでデータが出入りする。最初に取込/送出のどちらの話かを整理すると誤解が消える。

① 取込（INTO ME）= 連携提案の主役

ecforce などの顧客データ → ME のカスタム属性

ecforce / 顧客DB──▶ME（API受信）

配信のセグメント・出し分けに使う属性（購入有無、定期、ID連携状況等）を入れる方向。連携案件のほとんどはこちら。

② 送出（OUT OF ME）= 別の話

ME の「Webhook機能」= 逆方向

ME（イベント発火）──▶外部API / 顧客システム

頻出の誤解：MEのWebhookは「MEから外部へデータを更新しに行く」機能。ecforce→ME の取込には使えない。

1. 取込の手段は実質 A・B の2つ（Webhook直送は不可）

「ecforce Webhookで発火→MEへ直送」は技術的にできない。提案では最初からA/Bの2択で考える。

手段リアルタイム性 ecforce側で必要なもの概要 / 使いどころ
A. API連携 リアルタイム 外部サービスAPI連携オプション（初期0円/月3万）＋連携企業様での開発 ecforce側プログラムが ecforce API でデータ取得 → ME API に書き込み。即時の出し分けが必要なときの本命。開発工数が発生。
B. CSV → SFTP → ETL 日次 CSV連携バッチ処理（個別実装・要見積）＋SFTPサーバ（顧客準備） ecforceが毎日0:30にCSVを自動出力 → 顧客のSFTPへ → MicoのETL(Reckoner)が取得 → ME。大量データに安全。実質日次。
×. ecforce Webhook 直送 — — 不可 送信先URL・ボディ(Liquid)は作れるが認証ヘッダーを付けられず、認証必須のME APIを直接呼べない。

⚠Webhook直送は成立しない（一次情報で確認済み）。ecforce Webhookの設定項目は「送信先URL・イベント・テンプレート（ボディ）」のみで認証ヘッダー欄が無い。よって取込は A（リアルタイム）か B（日次） の二択。出典：ecforce faq「Webhook機能」「Webhook テンプレート管理」。

2. A / B の選び方 — 「リアルタイム要否」で決まる（最重要Tip）

この一問でほぼ決まる。先にここを握ると話が速い。

Q. 即時の出し分けが必要？
（購入直後にRM切替・シナリオ出し分け 等）
▶ はい（リアルタイム必須）

A. API連携

  • ecforce側で外部サービスAPI連携オプション（月3万）契約＋開発が必要。
  • ecforce → ME API へ即時書き込み。
  • ecforce API は1日1万件制限に注意。
▶ いいえ（日次でOK）

B. CSV → SFTP → ETL

  • ecforceが毎日0:30にCSV出力 → 顧客SFTP → ETL取得 → ME。
  • 顧客はCSV連携バッチ処理（個別実装）＋SFTPサーバをご用意。
  • 大量データに安全。開発不要に近い。

★落とし穴Tip：「ETLは最短10分間隔で取れます」と言っても、ecforceのCSV出力が1日1回（深夜0:30）固定なので、Bはどう頑張っても実質日次。＝「リアルタイム＝B」では実現できない。リアルタイムが要件なら必ずA。

3. つまずきポイント / 提案Tips（よくある誤解）

Webhookは“双方向”ではない

MEのWebhookはME→外部の送出専用。ecforce→MEの取込には使えない。方向を最初に整理する。

ecforce WebhookでME APIは叩けない

認証ヘッダーを付けられない仕様。「Webhookで連携」=取込には不可。A/Bへ誘導。

中間サーバ(SFTP/S3)は顧客準備

Micoはセキュリティ方針で中間サーバを用意しない。B案では顧客にSFTPをご準備いただく前提で案内。

LINE ID連携はecforce標準機能

Social Plusは必須ではない。ecforceビルトインでUID取得可。まず標準機能から検討。

ecforce API は1日1万件制限

超過でHTTP 429・翌朝までロック。大量データはBが安全。A案でも件数設計に注意。

モールデータはUID紐付け困難

自社ECデータに限定するのが現実的。段階導入（自社EC→モール）を推奨。

4. 連携キー & データ設計 Tips

「何をキーに、何を入れるか」。最小設計で十分動くことが多い。

連携キー＝LINE UID

  • ecforceのLINEログイン（ID連携）でUIDを取得し、MEと突合。
  • 電話番号は変更・重複リスク、会員番号は突合ロジック要。UID推奨。
  • 顧客番号が連携されていれば「ID連携済み」と判定でき、Day0から出し分け可能。

推奨データ項目（最小）

  • 顧客ID（LINE UID） … 突合キー
  • 購入商品 … 商品別の出し分け
  • 定期ステータス（1回 / 3回定期 等） … アップセル判定
  • ID連携状況 … 連携済/未でのシナリオ分岐

アンケートでの属性収集は不要なケースが多い（ecforce側データで代替）。

5. Web タグ / GTM 連携 Tips

属性連携と合わせて提案すると行動データが取れ、施策の幅が広がる。初耳の顧客も多いので早めに共有。

タグは2種類

  • 全ページ共通タグ（土台） … LINEから遷移したユーザーの行動をMEが取得できる仕組み。
  • イベント別タグ … LP閲覧 / 商品詳細 / カート追加 / 購入 / お気に入り追加 など。

提案時の注意

  • カゴ落ち配信には「カート追加タグ」＋「サンクスページタグ」の両方が必要。
  • PV数の上限（例：200万PV）を確認。多くの場合は余裕。
  • 全ページに貼るかは顧客社内確認が要るので、サンプルと管理シートを早めに送付。

7. 提案の進め方チェックリスト

  1. 実現したいこと・ユースケースをすり合わせ（Day0配信、購入後の出し分け 等）。
  2. 連携キーと項目を確定（UID＋購入商品＋定期ステータス＋ID連携状況 が基本）。
  3. リアルタイム要否を必ず確認 → A / B を決める（ここが分岐の肝）。
  4. A案ならecforceを交えた3社MTGでAPI仕様・オプション・開発を確認。
  5. B案なら顧客のSFTP準備とCSV連携バッチ処理（個別実装）を見積もり。
  6. Webタグ/GTMのサンプル・管理シートを共有し、貼付範囲を社内確認してもらう。
  7. テスト → リリースへ（リリースと並走で進行）。

8. 適用例：ジェイフロンティア様

上記Tipsを今回案件に当てはめた状態（2026/06時点）。

結論：リアルタイム必須 → A案（API連携）

  • 外池氏がリアルタイム連携を明言：購入後すぐにリッチメニュー切替、購入直後に商品別シナリオを出したい。
  • B（日次）では要件を満たせない（CSV出力が0:30固定＝実質日次）。
  • A案実現にはecforce側でAPI連携オプション契約＋開発が必要 → ecforceを交えた3社MTGで方式確定へ。

前提・データ設計

  • ゴール：LINEログインでUID取得 → ID連携有無でDay0から配信最適化。
  • 連携項目（4つ）：顧客ID・購入商品・定期ステータス(1回/3回)・ID連携状況。外池氏が認識相違なしと確認。
  • Mico側は現契約プラン内で対応＝追加料金なし。

✓ネクストアクション

  • Webタグのサンプル（共通＋個別）を外池氏へ送付（福田）。
  • Webタグ管理シートのURLを共有（矢澤）。
  • リアルタイム可否・方式確定のため ecforce含む3社MTGを調整（矢澤）。候補日はChatWorksで連絡。
