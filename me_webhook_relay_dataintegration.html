ME Webhook機能 / Webhookリレー / データ連携 の違い

Mico社内・営業用 / 混同しやすい3つを切り分ける ＋ Refa（MTG様）適用例

核：3つは「全くの別物」 Refa：Mii＋ME＋SFMC の共存構成 リリース想定：2026/08/01 更新：2026/06

0. まず結論：この3つは別物（混同しない）

「Mico Webhookでデータ連携」という言い方が混乱の元。Webhookリレーとデータ連携は仕組みも運ぶ中身も違う。ME Webhook機能はさらに別。

① ME Webhook機能

ME → 外部へ「実行」

ME(発火)▶外部API/顧客システム

MEの内部イベントを起点に、外部APIを叩いて顧客システム側を更新・実行する送出方向の機能。LINEイベントの中継でも、ME保有データの一括連携でもない。

例：Porters連携
LINEフォーム回答時に、ME側で属性を更新しつつ同時にPortersへWebhookを発火し、Porters上に新規レコードを作成。
LINEフォーム回答▶ME属性更新＋Porters Webhook→新規レコード
② Webhookリレー

LINEイベントを「素通しで分配」

LINE▶リレー(ME側)▶ME / SFMC

LINEから来るWebhook通知をヘッダー含め一切加工せずそのまま複数の外部URL（ME・SFMC）へ転送。MEやMiiで取得した独自データは含まない。

③ データ連携（API / ETL）

外部 ⇄ ME でデータを「やり取り」

SF / 外部DB⇄ME / Mii

CSV/ETL/APIで連携。外部→ME（取込）がむしろ主流：例 SFのステータス（ID連携有無・既存/未顧客）をMEに入れて出し分け。ME→外部を含む双方向はETL(Reckoner)が対応。キーはUIDのほか Mico ID・顧客ID・電話番号・メールアドレス等。

例：SFステータスの取込
SFが持つ「ID連携有無」「既存/未顧客」等をMEのカスタム属性へ連携 → MEでセグメント配信・リッチメニュー出し分けに活用。

⚠最頻出の誤解：「Webhookリレーを通せばMEのアンケート結果などもSFMCに渡る」は誤り。リレーはLINEイベントの素通し転送のみで、MEの属性データは含まない（類似のファーマフーズ様案件で確認済み）。

MEのデータを外部（SFMC等）で使うには別途連携が必要。手段は2つ：③データ連携(API/ETL)でデータを渡す／①ME Webhook機能で外部APIを叩く（フォーム回答等のカスタム属性を載せられる）。ただし①でやりたいことが実現できるかは相手側＝SFMCのAPI仕様による。

2. Webhookリレーの中身（②）

仕組み

  • ME側にリレーサーバを用意。1つのLINE公式アカウントのWebhookをここで受ける。
  • 各OAのチャネル情報でリクエストを判定し、MEとSFMCの双方へ振り分け転送。
  • 転送はヘッダー含め無加工の素通し。テーブル形式の引き渡しではない。

運用上の注意（社内方針）

  • リレーサーバ障害（ダウン・遅延）時にイベントが届かない等、責任分界点が難しい。
  • 社内方針として積極的に推奨・提案するソリューションではない。
  • 提案・実施時は障害リスク／責任分界点を顧客に説明し、免責合意が必須。

3. データ連携(API/ETL)の中身（③）— 双方向

実務では外部→ME（取込）が主流。双方向更新はETL(Reckoner)が対応（API/CSVは基本「MEの更新＝取込」方向）。名寄せキーはUID以外にも複数あり、取得方法も5種類。

外部 → ME（取込）★主流

  • SFなど外部DBのステータスをMEのカスタム属性へ取込。
  • 例：ID連携の有無 / 既存・未顧客 / 購買ステータス 等。
  • → MEでのセグメント配信・リッチメニュー出し分けに活用。

ME → 外部（書き出し）

MEの実データをSF/SFMC等へ。DWH連携時、キー（UID等）で以下が渡せる：

  • カスタマー情報（基本属性・カスタム属性）
  • LINE配信ログ、クリックログ、開封ログ
  • postback受信ログ
  • LINE友だち登録ログ、LINEブロックログ
  • アンケート配信ログ、回答開始ログ、回答完了ログ

出典：『勉強会用：データ連携』Slide 19

連携手段（3種）

  • CSV連携：手動・追加費用なし。MEの更新（取込）のみ。即時性は弱い。
  • ETL（Reckoner）：ノーコード自動・双方向更新可・5分〜日次。月10万／構築約3ヶ月。
  • API連携：リアルタイム・MEの更新（取込）のみ。クライアント側開発が必要（レート制限：1秒10回／1実行100件）。

名寄せキーと取得方法

キー候補：UID / Mico ID / 顧客ID / 電話番号 / メールアドレス

取得方法5種：① QR(パラメータ付URL) ② LINEログイン ③ Webタグ(GTM)で顧客番号取得 ④ アンケート回収 ⑤ オペレーター手入力。※電話/Email突合は誤連携リスクに注意

4. LINE Webhook の「向き先」3パターン

1つのLINE OAのWebhookをどこに向けるかで、できること／できないことが変わる。

向き先結果
MicoのみSFMC側でLINEのリアルタイムイベント（友だち追加・メッセージ受信等）が受け取れない。
SFMCのみME側でイベントを受け取れず、MEの基本機能（RM出し分け・シナリオ配信・アンケート回収）が正常動作しない。
Webhookリレーで双方両システムでLINEイベントを受け取れる。ただしME/Miiで取得・加工したデータをSFで使うには別途データ連携が必須。

5. 適用例：Refa（MTG様）

SFMCでメッセージ配信を想定。Mii・ME・SFMCを共存させたい構成（2026/06時点・新規検討、200万件想定）。

想定ユースケース（先方提示）

LINE▶ Mii（顧客管理・店舗QR別配信）▶ API ME（シナリオ配信）▶ データ連携 SF / SFMC（LINE/メルマガ/AppPush配信）
  • Mii：LINE接点を集約、店舗からQRごとに担当者を分けて配信のみ（1on1なし）。
  • Mii → ME：顧客データを反映（タップ等を見てシナリオ配信）。方式は要確認（CSV/ETL/APIのいずれか。津村氏メモでは「API連携」と記載だが未確定）。
  • ME → SF：データを戻したい（先方は「Mico Webhookで？」と認識）。手段は①ME Webhook(外部API実行)か③データ連携(API/ETL)。MEデータをSFで使う整理が必要。
  • SFMC：LINE/メルマガ/AppPushを配信。「LINE Webhook活用」＝SFMCがLINEのWebhookイベントを受け取りたい意（要確認）→ だから“LINE Webhookの向き先”＝Webhookリレーが論点になる。

3つの質問への回答

Q1. SFMCへ渡せるデータは？

手段で別物。リレー＝LINE標準イベントのみ（ME独自データなし）。データ連携(API/ETL)＝第3章のテーブル（カスタマー属性・各種ログ・アンケートログ等、UID等のキー）。

Q2. 並列で実現可能？

技術的に可能。Mii→ME（API）、ME⇔SFMCのLINEイベント共存（リレー）、ME→SF（API/ETL）をそれぞれ別建てで構築すれば並走できる。

Q3. Webhook(リレー)を提案して良い？

提案自体は可能だが積極推奨ではない。必要な場合は障害リスク・責任分界点を説明し免責合意が前提。

総括

本要件は ①Webhookリレー構築（LINEイベントを双方へ）＋ ②API/ETLデータ連携構築（MEの実データをSFへ）の2系統を別々に設計する必要があり、構成が複雑。お客様・ベンダー含めた慎重な要件定義を推奨。
